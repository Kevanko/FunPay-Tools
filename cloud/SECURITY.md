# Приватные профили синхронизации

`/v2/s/p_<64 hex>` требует `Authorization: Bearer <64 hex>`. Адрес и токен генерируются независимо через `crypto.getRandomValues`. Worker хранит SHA-256 токена. Публичный FunPay user ID и старый SHA-256 от него не являются ключом доступа.

Перед обновлением Worker выполните `schema.sql`: новая таблица `private_profiles` создаётся отдельно. Старые `profiles` не удаляются. API `/s/:id` возвращает 410; неподтверждённая запись `/nick/:uid` возвращает 403. Публичный список оформлений остаётся доступным только для чтения. Нельзя восстановить безопасное владение старым публичным профилем только по знанию ID: автоматического присвоения таких записей нет.

Порядок миграции:

1. Сохранить резервную копию D1 и локальный `.fpconfig` на каждом устройстве.
2. Применить схему, затем обновить Worker и расширение. Настройки на устройствах остаются локально; новая синхронизация начинает с них.
3. Для переноса между устройствами экспортировать отдельный `.fptsync` и импортировать его на устройстве с тем же FunPay аккаунтом. Новый QR входа в Android передаёт тот же ключ внутри зашифрованного пакета; приложение подключает его после проверки аккаунта на FunPay. Ключ не входит в обычный экспорт настроек.
4. Если нужные настройки остались только в старой D1 записи, оператор вручную подтверждает владельца вне публичного API и переносит bundle в новый случайный приватный профиль. Старую запись сохраняет до проверки восстановления; её нельзя автоматически закреплять за первым заявившим user ID клиентом.

Экспорт/облако используют allowlist настроек автоответчика. Пароли аккаунтов, cookies, ключи облака, остатки товаров авто-выдачи, бонусные коды и журнал отправки не переносятся. При применении настроек существующий локальный runtime автоответчика сохраняется.

Эти изменения подготовлены в исходниках. Применение схемы и Worker к действующему облаку требует отдельного развёртывания.
